# Classic-UI performance baseline — 2026-10-22

Measured with `backend/tests/perf/capture_baseline.py` (TDD'd harness
`tests/perf/harness.py`) over the in-memory fake Firestore, seeded by
`tests/demo_server.seed` with a realistic day:

- **Seed volume:** 7 occupied rooms (+2 add-ons), ~11 finished-stay bills, ~12
  customers, 1 settle-later, 1 expense, ~36 total rooms.
- **`Cold reads`** = ground-truth Firestore document reads for one *uncached*
  load (server caches busted first), from the fake's thread-safe `_Store` —
  thread-complete, so it counts reads made inside `/get_data`'s
  `ThreadPoolExecutor`. **This is the enforced budget** (deterministic,
  backend-independent, maps to cloud read cost).
- **`Header reads`** = what the production `X-Firestore-Reads` header reports
  for the same call. A gap vs `Cold reads` = reads happening off the request
  thread, invisible to production monitoring.
- **`p50/p95 ms`** = local wall-clock over 30 calls, warm where the screen
  caches. **Relative only** — the fake has no network, so these are NOT
  production latencies.

## Confirm / exonerate the brief's named suspects

- **`/get_data` (front desk): CONFIRMED target.** Its prior optimization cut the
  *transaction-log download* and parallelized the fetch (good for latency), but
  the **read count is still ~67 per cold load**, dominated by the full rooms
  collection scan (~36 reads). Caveat: in production the rooms grid is normally
  fed by a client-side Firestore **listener** (per `CLAUDE.md §4`), so 67 reads
  is the **boot/fallback** cost, not a per-15s cost.
- **`/get_history`: EXONERATED** — 3 reads, already minimal.
- **`get_customer` / customer search: EXONERATED** — 4 and 6 reads, already
  indexed and minimal.

## Independent finding — production read monitoring is blind to the busiest screen

`X-Firestore-Reads` reports **0** for `/get_data` and **2** for `/dashboard`
while the true cost is **67 / 69**. The counter is contextvar-scoped
(`core/metrics.py`); the reads happen inside the hand-rolled
`ThreadPoolExecutor` in legacy `/get_data`, whose worker threads don't inherit
the request context. (Paths that use Starlette's `run_in_threadpool` — e.g.
`/reports/summary` — DO copy the context, which is why their header matches.)
So `GET /api/v2/admin/metrics` under-reports the front desk's real read load.
Fixing the instrumentation to copy context into that executor is a separate,
low-risk improvement worth doing alongside.

## Recommended first-slice fix targets (await confirmation)

1. **Room tariffs (`/rooms/tariffs`), 47 → ~0–1 reads.** Reference data (room
   base prices, AC surcharge, categories) that rarely changes → read-through
   cache with explicit TTL + invalidation on the settings/room write path.
   Lowest risk, highest certainty, no money/tax surface.
2. **Front desk `/get_data` rooms scan (~36 of 67 reads).** Highest-frequency
   screen. Investigate whether the full-collection room scan can be reduced
   (it already caches 30s). Needs care — it feeds the rooms grid.
3. **(Optional) Fix the contextvar/ThreadPoolExecutor undercount** so
   `/admin/metrics` tells the truth about the front desk.

Secondary / later iterations: reports overview (66 reads, low frequency),
transactions (19).

## First slice shipped (2026-10-22)

Two fixes, each TDD'd and flag-guarded; money/tax parity byte-identical.

> **Scope note (corrected 2026-10-22):** `static/*.js` shows the classic UI
> never calls `/api/v2/rooms/tariffs`, `/dashboard`, `/reports/*`,
> `/settlements`, or `/transactions` — those are **React-SPA-only** endpoints
> (`UI_MODE=classic`, SPA parked). The classic UI's `/api/v2` usage is limited to
> `auth/*`, `bills/*`, `customers/*`, `settings/invoice`, `authorize`,
> `client-errors`, and `admin/metrics`; everything else it loads via **legacy
> routes** (`/get_data`, `/get_history`, and legacy reports/settlements/
> transactions/banking/staff/register). The ranked table above therefore mixed
> classic and SPA endpoints; see the corrected legacy-only baseline below.

| Fix | Metric | Before | After | Scope |
|---|---|---:|---:|---|
| **Tariffs reference-data cache** (`PERF_TARIFFS_CACHE`, default on) | `/rooms/tariffs` reads after a checkin/payment invalidates the shared rooms cache | **47** | **0** | **SPA-only** — the classic UI does not call this endpoint; excluded from the classic-UI scoreboard. Kept as a safe free win for the parked SPA. |
| **Monitoring context propagation** (no flag; behaviour-preserving) | `X-Firestore-Reads` header for `GET /get_data` | **0** (blind) | **67** (true) |
| | `X-Firestore-Reads` header for `GET /api/v2/dashboard` | **2** (blind) | **69** (true) |

- **Tariffs:** `get_all_rooms()` is `@cached(ttl=30)` but invalidated on every
  checkin/payment, so tariffs re-scanned all rooms after each room write. The
  dedicated cache (TTL 300s, reference data) removes that re-scan. Flag off =
  exact previous behaviour. Note: idle repeat calls were already free via the
  30s cache — the win is specifically the post-write re-scan at a busy desk.
- **Monitoring:** `/get_data`'s hand-rolled `ThreadPoolExecutor` didn't inherit
  the request context, so `count_reads` in its worker threads was a no-op and
  `X-Firestore-Reads` / `/admin/metrics` reported 0 for the busiest screen. Now
  a fresh context copy is propagated per task; the header reflects the real
  cost. No change to data, reads issued, or the response.

**Not changed this slice (deferred):** the front-desk `/get_data` rooms-scan
read count itself (67), reports overview (66, low frequency), transactions (19).

**Gates:** backend `pytest` 263 passed / 6 xfailed; legacy suite 637 passed;
`test_parity.py` + perf 14 passed. Frontend vitest/typecheck and classic-UI
ESLint were not run — no `frontend/` or `static/*.js` files changed this slice.

### `/get_data` — investigated, left unchanged (inherent, with evidence)

Root-cause of the 67 reads: `get_all_rooms()` is a **single optimal stream**
(1 read/room) feeding the room grid, plus today's payments (~27) feeding the
**Transactions tab**, plus totals + today's expenses. All are consumed by the
classic UI:
- the grid needs every room's live doc, and after a checkin the re-read is
  *correct* (occupancy changed);
- `transaction-tracking.js:3416-3448` renders the Transactions tab from
  `logs.cash / online / refunds / expenses`, set from `/get_data`'s response
  (`script.js:1645 CibaraState.setLogs(data.logs)`). The in-code comment
  claiming "the frontend only reads `logs.renewals`" is **stale** — trimming
  the payments fetch would break the Transactions tab.

So `/get_data`'s reads are **inherent to its payload**, not an N+1 or a
fixable scan. They are already mitigated by the 30s `get_all_rooms` cache and,
in production, the client-side Firestore listener (`/get_data` is boot/fallback,
not per-15s). No safe reduction without an architecture change (out of scope /
zero-cost). The **monitoring fix** (first slice) at least makes its real cost
visible in `/admin/metrics`.

**Bigger classic-UI targets remain** for a later slice: `/insights/summary`
(101) and `/get_register_data` (81) — both above `/get_data` by raw reads and
not yet root-caused.

## Third slice shipped (2026-10-27) — insights + register

Root-caused per-query (fake seed: rooms 47, payments 18, bills 12, audit 23).
**The single biggest component of BOTH screens is the 47-read full
`get_all_rooms()` scan** — the same scan behind `/get_data`. Tests:
`backend/tests/test_classic_perf_slice3.py` (4, TDD'd). Owner-approved scope:
fixes 1+2+3 (not the register-checkin targeted-rooms query, fix 4 — deferred).

| Fix | Metric | Before | After |
|---|---|---:|---:|
| **Monitoring context propagation** (no flag; behaviour-preserving) | `X-Firestore-Reads` for `GET /insights/summary` | **~47** (missed its `_POOL`) | **true** |
| | `X-Firestore-Reads` for `POST /get_register_data` | **~1** (missed its pool) | **true** |
| **Insights rooms → count() + status==cleaning** (`PERF_INSIGHTS_ROOMS_LIGHT`, default on) | `/insights/summary` cold reads (31d) | **101** | **58** |
| **Register checkout drops the unused rooms fetch** (`PERF_REGISTER_SKIP_ROOMS_CHECKOUT`, default on) | `POST /get_register_data` `mode=checkout` cold reads (31d) | **81** | **34** |

- **Monitoring:** `/insights/summary` runs audit/payments/bills on its own
  module `_POOL`; `/get_register_data` fans every fetch onto a `max_workers=16`
  pool. Neither inherited the request context, so `X-Firestore-Reads` /
  `/admin/metrics` reported ~0–1 (same blindness the first slice fixed for
  `/get_data` only). Each `pool.submit` now runs via `contextvars.copy_context().run`.
  **Directly relevant to Task 3:** before this, prod metrics showed these two
  busy screens as deceptively cheap.
- **Insights rooms:** insights needs only the room COUNT (occupancy
  denominator) + the `cleaning`-now strip — never the full room docs. A
  `count()` aggregation (0 reads) + a single-field `status=="cleaning"` query
  replaces the 47-doc scan. Payload byte-identical (test asserts it). Flag off =
  old full scan.
- **Register checkout:** in `mode=checkout` the rooms snapshot is never consumed
  (active rooms excluded; stay-payment prefetch is checkin-only) — a pure
  full-collection dead read. Skipped. Payload byte-identical. Flag off = old
  fetch. **Checkin mode is unchanged** (it genuinely iterates occupied rooms; a
  `status=="occupied"` query there is fix 4, deferred by owner).

**Inherent / not touched:** the audit/payments/bills *range* scans — driven by
the report **window size** (a 31-day window was measured; a "today"/"7d" default
reads far less), not reducible without a composite index or changed semantics.
Tightening the classic UI's default window is a separate visible behaviour
change (owner sign-off) — noted, not done.

## Fourth slice (2026-10-28) — ID-doc previews + "Update payment" profiling

Targets the two surfaces reported slow on prod: guest-search ID-doc images and
"Update payment". Each change flag/behaviour-guarded; money/tax untouched.

### Shipped — ID-doc grid previews load `thumb`, not watermarked `view`

| Metric (per preview tile) | Before (`view`) | After (`thumb`) |
|---|---:|---:|
| image payload | 184,417 B | 2,854 B (**98% smaller**) |
| Firestore writes (`views`/`last_viewed`) | 1 | 0 |
| audit writes (`customer_doc.view`) | 1 | 0 |
| server work | watermark RGBA tile + q88 re-encode | plain resize |

- The Register guest-doc grid (`static/register.js`) fetched each preview tile
  as `view`: the server watermarks + re-encodes the full-size image AND writes a
  Firestore `views`/`last_viewed` update + a `customer_doc.view` audit entry per
  tile. Opening a 4-doc guest = ~738 KB + 4 re-encodes + 4 writes + 4 audits,
  just for thumbnails.
- Now the grid requests `thumb` (plain resize — no watermark, no Firestore
  write, no audit). The full watermarked `view` is loaded only on click, in the
  lightbox (`openPhotoViewer`, already thumb→view). `CibaraSecureImg.src()`
  default hardened `view`→`thumb` so an omitted variant can never hit the
  expensive/audited path; the two full-view callers pass `view` explicitly.
- **No server or upload/archive change.** `id_docs.read_image` already serves
  `thumb` cheaply; `test_view_is_watermarked_counted_and_audited` already asserts
  thumbnails are neither watermarked nor counted as views. `sw.js` cache v9→v10.
- The three other doc grids (check-in preview, viewer strip, customer-manager)
  already used `thumb` — this was the one outlier. Numbers from
  `make_thumb()`/`watermark()` on a 2400×1512 sample at stored quality.

### Investigated — `/add_bill_payment` ("Update payment"): read-lean, write/CPU-bound

Profiled with the fake-Firestore `_Store` counters (amount-only call, no discount):

| Case | Ground-truth reads | Writes | Header reads |
|---|---:|---:|---:|
| Old bill, no linked settlement (hot path) | 5 | 6 | 4 |
| Pay-later bill with linked settlement | 6 | 7 | 5 |

- Reads are: the single `bills_ref.document(bill_id).get()`, the
  `@guard_duplicate_submit` idempotency read, the `payment.edit` permission, the
  payment-write service, and (only when linked) one settlement `.get()`. **None
  is redundant within the handler, and none is parallelizable** — the settlement
  read depends on the `settlement_id` the bill fetch just returned, so there is
  no independent read to fan out.
- The real cost is the **6–7 sequential writes** (bill update, totals batch
  commit, payment doc, audit log, settlement update) issued as separate Firestore
  round trips on one vCPU, plus `recompute_bill_gst` CPU **only when a discount
  is applied**. That is CPU/write-round-trip contention — exactly what the
  owner's 2-vCPU bump addresses.
- **No code change made.** Cutting a read would mean editing shared
  money/auth/service code (`payment_service`, the permission decorator, the
  duplicate-submit guard) — §2 preserved-logic surface with its own parity test —
  to save at most one read. The only write-side win (batching the independent
  writes into one atomic commit to save round trips) changes money-write
  atomicity/ordering and duplicate-guard recovery semantics; it would need its
  own flag + a `test_parity` run + owner sign-off. Documented, not forced.

### Shipped — pause live Firestore listeners while the tab is hidden

~12 front-desk tabs stay signed in but only 1–2 are in use. Each kept all 9
`onSnapshot` listeners live, so every remote change (each payment/check-in on
the active tabs) woke every hidden tab to re-render an off-screen grid and,
across devices, pay billed reads for the delta — idle background load.

- `google_sync.js` now **detaches** all listeners on `visibilitychange`→hidden
  and **re-attaches** on →visible. Each `onSnapshot(...)` is wrapped in
  `_track()` so its unsubscribe is captured; `_detachLiveListeners()` calls them
  all; `_reattachLiveListeners()` re-runs `startListeners(fullAccess)`. Firestore
  delivers the current snapshot on re-attach (from the IndexedDB cache + resume
  token), so the grid self-heals. In **legacy** mode each listener deliberately
  skips its first snapshot, so re-attach also calls `fetchData()` once to
  repaint; in **listener-first** mode the first snapshot seeds+paints, so no HTTP
  call is made. Flag-guarded, default ON; per-device kill switch
  `localStorage['cibara_pause_hidden_listeners']='0'`.
- There is **no `/get_data` 15s poll in the classic UI** to stop — that is the
  SPA dashboard (CLAUDE.md §4). A hidden classic tab's only idle background load
  is these listeners.
- **Verification note:** the real detach/re-attach cannot be exercised locally —
  the in-memory demo has no live Firebase (listeners are permission-denied, see
  `demo_server.py`), so this needs a UAT check. Verified locally: `node --check`
  + ESLint (no-undef) pass; the classic UI boots with the edited file (every
  script 200, grid paints, sw.js v9→v10 re-fetch confirmed); and firing
  `visibilitychange` in both directions, flag on and off, never throws and leaves
  the DOM intact.
